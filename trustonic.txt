Overview
This document describes the Telecoms Platform public API method and its specifications. It is
intended for operators who intend to integrate with the Telecoms Platform system to manage the
devices within the Telecoms Platform system. The API is designed to be simple to integrate with
and provide the necessary operations to register and manage the devices within the Trustonic
Telecoms platform.

URI Method and Definition
RESTful uses standard HTTP methods to operate resources. The standard HTTP methods are as
follows:
Parameter

Description
The following enumerated values are supported:
POST: Create resources.

HTTP Method PUT: Replace resources.
PATCH: Modify resource attributes.
GET: Query resources.
DELETE: Delete resources.

Rate limiting of API
A "rate limit" is the number of API calls that can be made within a given time period.

It helps us provide reliable and scalable API services to protect your operation from erratic and
unpredictable spikes in the rate of requests.
Telecoms Platform sets the rate limit such that an API can be called up to 100 times/minute
using the single API token.
If your application exceeds the request limits detailed above, the Telecoms Platform will return a
429 — "Too Many Requests" error message and the new API calls will need to be made again.

Batch Processing
The Device management APIs support Batch Processing and it is designed to handle bulk
requests efficiently. Depending on the size of the list in the request body, the processing is
handled either synchronously or asynchronously.




Synchronous Processing:
If the request contains a list with fewer than or equal to 100 items, the system processes
the request synchronously and returns a response with the result directly.
Asynchronous Processing:
If the request contains a list with more than 100 items, the system processes the request
asynchronously. In this case, the API returns additional parameter batchActionId and
batchActionStatus. batchActionId can be used to query the status of the batch operation
status using Batch Action status (GET /api/v2/query/batchAction) API.

Authorization

1.1

Get Access Token

API-Key will be used to get the Access/Bearer Token from Telecoms Platform. API-Key is
unique per user account in Telecoms Platform. Depends on the user access role in Telecoms
Platform, Access/Bearer Token can be used for multiple tenants. User can use the tenantId in
request header to perform the API Operation for specific tenant. When tenantId is not included in
the Header, API operation will be performed on the users default tenant account.
POST api/v2/authorization/token

Token received must be used as Authorization bearer in all API Method’s Header.

7

Webhook Notification API

The Telecoms Platform Webhook Notification API allows to send change notifications to a
subscribed client about the completion of any subscribed events or background processes. On
completion, the operation results from the Telecoms Platform services API operations are shared
with the requesting client as a change notification. The result-sharing process is based on an
efficient asynchronous workflow that avoids locking computational resources and, therefore,
prevents inefficient event dependencies.

A Webhook push is simply a HTTP POST request, sent to the URL of your choosing. The push
is automatically triggered when data updates.

The following procedure summarizes the Webhook Notification API workflow:
1. The client can create an event with the Webhook Notification. For example, an event
could be registering device into service or changing the device state such as locked,
active, enrolled .
2. The webhook notification event is now registered. A database stores the event
notification subscription and the associated event.
3. The client makes a call to inventory upload API or Activate/deactivate service API with
list of devices. The API operation in Telecoms Platform triggers an asynchronous event
for batch of devices.
4. Telecoms Platform performs a database lookup to get the Notification events and check
the event status in configured intervals.
5. Based on event status, Notification will send to URL registered in the Webhook
Notification request.

Callback Method
This webhook listens for state changes of devices and provides the real-time webhook
notifications to web application:
POST {$request.body#/url}

Callback Payload
The webhook notification will return one of the following status:
actionCompleted: Indicates that the action has been completed successfully, and the device
state has changed or has been successfully
actionFailed: Indicates that the action has failed and the device state change is failed.
Payload:
Body
deviceUid

Device Unique Identifier
Specifies the name of the transition state.

eventType
ENUM {idle, readyForUse, enrolled, active, locked, released}
actionName

Specifies the action being performed on the device (e.g., upload, register,
deregister, lock, unlock, reload, release ).

status

Provides the status of the action (actionCompleted, actionFailed).
Indicates the type of service associated with the device

serviceType

Enum {inventory, supplyChain, deviceFinancing, simControl, theftProtection,
subsidyProtection}

updatedAt

The date and time of when the action was completed or failed.

failedReason

Describes the reason for failure when an action or upload does not complete
successfully (e.g., 1st party error).
